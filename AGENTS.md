## Database (Neon)

- Staging project `dommus-negotii-staging` (`rough-voice-82311957`), linked in `.neon`. Branches: `main` (staging data), `dev` (local `next dev`, via `.env.development.local`) and `test` (throwaway, for `tests/integration`, used by local runs and CI). Production is a separate project, created later.
- `.env.local` holds four URLs: `DIRECT_URL` (owner, migrations), `DATABASE_URL` (app_runtime, pooled — the app), and the same pair as `TEST_DIRECT_URL` / `TEST_DATABASE_URL` for the `test` branch. CI gets the test pair from the GitHub repository secrets of the same names.
- **Never run `neon env pull`, or `neon link` / `neon checkout` without `--no-env-pull`.** They write the owner role into `DATABASE_URL`, which would bypass the app_runtime grants (PRD §5).
- Migrations: `npx prisma migrate deploy` (uses `DIRECT_URL`). After creating a new branch, run `node scripts/set-runtime-password.mjs .env.local <VAR> <OWNER_VAR>` to give it an app_runtime URL.
- Prisma does not wrap a migration in a transaction, so **write every new migration.sql between `BEGIN;` and `COMMIT;`**: a dropped connection then leaves nothing half-applied. For the older, unwrapped migrations, a P3009 after a drop means: check which statements took effect (tables, indexes, constraints), apply only the missing ones, then `npx prisma migrate resolve --applied <name>`. Never re-run the whole file.
- Interactive transactions pass `TX_OPTIONS` (`src/lib/db.ts`); Prisma's 5-second default is too short over Neon from here. Bulk imports use their own longer limit.
- Ledger, audit, evidence and settings rows are append-only, even for the owner. Test rows can't be cleaned up, so reset the `test` branch from `main` instead.
- Local test logins (Admin, Cashier, both with TOTP) live on the `dev` branch; their credentials are in `.env.development.local`.
- Skills: `neon`, `neon-postgres` (`.claude/skills`, pinned in `skills-lock.json`). Check them with `neon skills status`.

## Settings (PRD F2)

- `src/shell/settings/`: `definitions.ts` lists every setting (financial or operational, kind, PRD default, range); `settings.ts` reads values and handles changes. Read a value with `getRateSetting` / `getCountSetting` / `getDateSetting` (as of a Lagos date); never hard-code a limit that is a setting.
- The value in force on a date is the `shell.setting` row with the latest `effective_from` on or before it (latest `created_at` wins on the same date), else the PRD default. Rows are append-only. Proposals never count until approved (AT-r).
- Financial settings: Admin proposes (value, effective date not in the past, reason); Management approves or rejects; the proposer may withdraw. Nobody approves their own proposal, a proposal whose date has passed can't be approved, and only one proposal per setting may be open (partial unique index `setting_change_request_one_pending`, Prisma preview feature `partialIndexes`).
- The service functions take `today` as a parameter: tests use random dates centuries ahead because test rows can't be deleted.

## Loan engine (PRD F6)

- Pure, no I/O: `src/modules/credit/domain/schedule.ts` (planned schedule, indicative calculator), `allocation.ts` (allocation helpers, `diffAllocations` for recompute), `recompute.ts` (`computeLoanState`, `payoffQuote`). Money is bigint kobo, rates bps; the lint rule and `tests/unit/no-float-money.test.ts` forbid floats there.
- `computeLoanState(terms, payments, asOf)` replays payments by payment date, then posting order. Each cycle is done in two passes: first the principal arrears the cycle's payments clear (fixes the interest base Bk, the grace window), then the allocation (arrears oldest first, interest before principal → cycle interest → cycle principal → prepayment re-spread → Overpayment Credit after closure).
- `payoffQuote` simulates a pay-everything payment, so the quote always equals what closes the loan.
- `tests/unit/loan-engine.test.ts` holds PRD cases A–I and AT-a/o/s/m; keep them passing exactly.
- Legacy loans start the computation at the go-live date (d0). `LoanTerms.openingArrears` (`{ principal, interest }`, from `loan.opening_arrears_principal/interest`) adds instalment 0, due on d0: `planSchedule` lists it first and spreads only the rest of the principal; `computeLoanState` puts it at the head of `dues`, so it is overdue from the day after d0, cleared first (interest before principal), and its unpaid principal stays in the interest base like any principal arrears. `instalmentLabel(0)` reads “Arrears at go-live”. Loans without arrears are unchanged.
- Ledger bridge: `src/modules/credit/loans/repayments.ts`. A loan's payments are its remittance rows (not credit rows, not reversed), ordered by payment date, then schedule `postedAt`, then row number. `planRecompute` diffs the engine's allocations against the posted ones (originals not yet reversed, read back from event metadata `rowId/kind/installment/paymentDate`); `applyRecompute` reverses what changed (`CREDIT:REV:<eventId>`), posts the rest (`CREDIT:ALLOC:<row>:<kind>:<k>:<amount>:<trigger>`) and closes or reopens the loan as `system`. `loanLiveState` feeds the loan pages (balance, arrears, repayments with their split, payoff quote).

## Loan workflow (PRD F7)

- State machine: `src/modules/credit/domain/loan-status.ts` (the PRD table; pure). Services in `src/modules/credit/loans/`: `applications.ts` (member draft/submit/cancel, Loan Officer assisted capture), `review.ts` (verify, recommend, decline, approve, reject, cancel approved), `disbursement.ts` (Cashier prepares the voucher, Finance Manager verifies or returns), `queries.ts` (exposure panel, detail, lists), `common.ts` (`moveLoan`, limits, numbering, `loanTerms`).
- Every status change goes through `moveLoan`: checks the state machine, updates only if the status is unchanged (no lost races), writes `loan_transition` (append-only) and the audit trail.
- Limits (`max_open_loans_per_member`, `max_open_guarantees_per_guarantor`; keys kept, labelled “Active … per …”) count ACTIVE (paid-out) loans only; applications in review don't count. `assertWithinLimits(..., stage)`: submit refuses at N active; approve refuses when active + approved-not-paid (`AWAITING_PAYOUT`) reach N; payout (voucher preparation) refuses at N active. A loan never counts against itself. Member guarantors are keyed by MOAUM ID, non-members by phone (+234 form).
- The application carries the applicant's own bank account (`payout_bank`, `payout_account_no` (10-digit NUBAN, spaces removed), `payout_account_name`): required on submission and on assisted capture, optional on a draft; a new application starts from the member's last ones. The loan page flags an account name that doesn't match the member, and the Cashier's disbursement voucher is pre-filled from it (still editable: the voucher records where the money actually went). Legacy loans have none.
- Paying out anywhere but the application's account needs `accountChangeReason` (≥ 10 characters, stored on the voucher, `sameAccount` in `src/lib/nuban.ts`: same digits and same bank code); the Finance Manager's Verify card shows both accounts and the reason, plus notices for a beneficiary name unlike the member's (`sameName`, `src/lib/names.ts`) and a number that fails the bank check. Refunds show the same name and number notices at every stage (warnings only: the signed request decides).
- Approval fixes the rate in force that day (`rate_bps`). Voucher verification posts `CASH_OUT` (source `DISBURSEMENT_VOUCHER`, cash and principal = approved amount, bank account set), sets d0 = value date and stores the binding schedule, in one transaction. One PREPARED voucher per loan (partial unique index); preparer ≠ verifier; no self-dealing (`assertNotOwnLoan`).
- Loan numbers: `CSS-YYYY-NNNNN` from `credit.loan_number_sequence` (atomic upsert), issued at submission.
- MOAUM bank accounts (`credit.bank_account`, Admin page `/staff/admin/bank-accounts`) were added early because vouchers and the ledger need them; 1c adds statements and opening balances.
- Status notifications come in 1d.

## Legacy loans (PRD F8, adapted)

- `src/modules/credit/loans/legacy-import.ts`, pages `/staff/legacy-loans` and `/staff/legacy-loans/<batch>`. MOAUM keeps only, per loan, Name, PIN (the payroll staff number), Tenure (months left) and Principal (still owed at go-live), so there is no history to replay: each loan starts on the go-live date (d0 = go-live) with amount = what is owed, tenure = months left, rate = `rate_monthly_percent` or the interest rate setting at go-live (0 allowed: interest already included), and runs under F6 from there. This replaces the PRD's regenerate-and-compare step, which needs history MOAUM doesn't have.
- Members are matched by `payroll_staff_no` (or member number); they must exist and be ACTIVE first. A name that differs from the member record is a warning, not an error. Spreadsheet amounts are rounded half up to the kobo with integer arithmetic (`parseSpreadsheetNaira`); rounding is shown as a warning.
- Admin uploads (dry run as an `ImportBatch` of kind `LEGACY_LOANS`, header JSON with the go-live date and control totals); the Finance Manager commits (different user), only when the `go_live_date` setting equals the file's date and that date has arrived. Commit, all or nothing: new `CSS-YYYY-NNNNN` number (year of go-live), `legacy_account_no` = given or `LEGACY-<PIN>`, loan ACTIVE with its binding schedule, one `OPENING_BALANCE` (source `LEGACY_IMPORT`, `principal_amount` = owed, metadata with PIN, rate, tenure, the arrears, next due date), evidence link `LEGACY_IMPORT:<batch>`. No historic events, so pre-go-live interest only shows as revenue when overdue interest from the file is actually collected.
- Arrears at go-live (added 23 November 2026, MOAUM's choice): optional columns `arrears_principal` (already overdue, part of `principal`) and `arrears_interest` (already overdue, owed on top); blank = up to date. Stored on the loan (`opening_arrears_*`, CHECK ≥ 0 and principal part ≤ amount), shown on the dry run, and carried by the engine as instalment 0. Overdue interest, when paid, posts `INTEREST_INCOME` like any interest. The report "Legacy loans and opening balances" lists each loan's opening balance, what it was behind by at go-live and current outstanding, plus bank opening balances.

## Remittance schedules, Track A (PRD F9)

- `src/modules/credit/remittance/`: `source-advice.ts` (Finance Manager; header from the form, rows file `member_moaum_id, member_name, amount`, the source's document as PRIMARY evidence; all checks or nothing), `schedules.ts` (Treasurer: `previewSchedule` → `commitSchedule`), `common.ts` (`RemittanceError` carries a `details` list shown under the message).
- Schedule file: XLSX with a `Rows` sheet and an optional `Lodgements` sheet (template `/api/v1/templates/remittance-schedule.xlsx`); a CSV carries rows only. The header comes from the form. The dry run is an `ImportBatch` (kind `REMITTANCE_SCHEDULE`) whose `header` JSON holds the form input, checksum, raw lodgement lines, batch-level errors, the advice match and totals; rows go in `ImportRowLog` with their planned allocation.
- `validateSchedule` runs every PRD check: totals and count, reference unused for the source, one REGULAR per source and month (also a partial unique index), duplicate rows by `row_hash`, member ACTIVE or EXITED, loan resolution (given number: the member's ACTIVE loan, or CLOSED → Overpayment Credit; blank: none active → credit, one → it, more → error), amount > 0, payment date not future / after the month / before d0 / before go-live, payroll totals per member equal the Source Advice (AVAILABLE, same source and month), lodgement key `account|REFERENCE|kobo|date` unused. Any error rejects the whole batch. DIRECT rows are refused until 1c (bank credits tagged to members, F10).
- Commit re-runs the checks, then in one transaction (`REMITTANCE_TX`, 5 min): advice → USED, schedule, rows, UNVERIFIED lodgements, `SCHEDULE_ACCEPTED`, `DEPOSIT_CREDITED` for credit rows (Member entity, `CREDIT:ROW:<id>:CREDIT`), each affected loan's recompute, `SCHEDULE_POSTED`, PRIMARY evidence link `REMITTANCE_SCHEDULE:<id>`, audit with checksum. `CommitHooks.beforeFinish` exists only so a test can force a mid-batch failure.
- Pages: `/staff/remittance` (advice and schedule upload, lists), `/staff/remittance/batches/<id>` (dry run and Post), `/staff/remittance/schedules/<id>`.
- **Payroll vouchers as they arrive** (`payroll-voucher.ts`): the payroll office's file (title row such as `OCTOBER 2026 SALARY VOUCHER`, then `S/NO, STAFF NAME, STAFF NO, <deduction column>`) is accepted unchanged for both the Source Advice and the schedule. The header row is found by its `STAFF NO` column; the month comes from the title and must equal the month covered; the amount is the one remaining column (or the one naming MOAUM); a TOTAL line is skipped. Rows are matched to members by `member.payroll_staff_no` on that remittance source, or by the system member number once payroll quotes it (`membersByPayrollKey`). A voucher has no dates, so the schedule form asks for the payment date.
- **Corrections** (`corrections.ts`): a `CorrectionBatch` on a posted schedule names live rows to reverse and/or replacement rows (payroll voucher or template file), with a reason and a document. Only the Treasurer who posted the schedule prepares it (`correction.prepare`); someone else with `correction.verify` (Finance Manager) verifies or returns it; one PREPARED per schedule (partial unique index). `evaluateCorrection` re-runs the row checks (`checkScheduleRows`, shared with schedules), refuses a replacement that repeats a remaining live row, and requires the rows left afterwards to match the schedule's current advice member by member (`matchAdvice`). Verify runs it all again, then in one transaction: rows get `reversed_at` (before replacements are inserted: `remittance_row_live_hash` is unique only among live rows), reversed credit rows' `DEPOSIT_CREDITED` is reversed, replacement rows are added after the last row number with `correction_id`, credit replacements post `DEPOSIT_CREDITED`, every touched loan is recomputed (trigger `CORRECTION:<id>`), a superseding advice takes over, evidence is linked PRIMARY to `CORRECTION:<id>`. Nothing is edited or deleted.
- **Superseding advice**: the Finance Manager uploads the source's corrected advice with `supersedes` + a reason. An unused advice is SUPERSEDED at once. The advice of a posted schedule stays USED; its replacement is reserved for that schedule's correction (a new schedule can't use it) and takes over when the correction is verified (`currentAdviceOf` follows the chain).
- DIRECT rows (a member's own transfer into MOAUM's bank) name a direct-payment tag in `bank_credit_ref`: the tag must belong to the row's member, be unused, and its credit equal `amount_paid`. Posting turns the tag into a BANK_VERIFIED lodgement of the schedule (uniqueness key `TAG:<id>`). DIRECT rows are not in the Source Advice match and can't be corrected yet.
- **The Source Advice is optional (changed 13 November 2026 at MOAUM's request).** A schedule whose advice reference is empty posts on the Treasurer's upload alone: `remittance_schedule.advice_id` is null, there is no member-by-member match, and its corrections are not matched against an advice either. When a reference is given, everything above still applies (AT-l). This relaxes PRD decision 13: without an advice nothing stops the Treasurer moving money between members inside a total, so the per-member SMS on posting (F15) is the remaining check.

## Refunds and reclassification (PRD F12)

- `src/modules/credit/refunds/refunds.ts`: a refund request (member at `/member/credit`, or a signed request captured by a Loan Officer at `/staff/refunds`) → Management approves or rejects → the Cashier prepares a REFUND voucher (`voucher.refund_id`, transfer evidence) → the Finance Manager verifies (not the preparer) or returns it. Verify posts `CASH_OUT` (source `REFUND_VOUCHER`, entity `Refund`, bank account) and `DEPOSIT_REFUNDED` (entity `Member`) in one transaction; the refund becomes PAID. One open refund per member (partial unique index `refund_one_open`); `refundableCredit` = credit less open refunds, re-checked at every step. Credits are only ever refunded, never applied to a loan. Staff never act on their own member record.
- `reclassifications.ts`: the Treasurer moves part of a posted repayment that went to principal into Overpayment Credit, with the member's request as evidence; the Finance Manager verifies. Allowed only before the next REGULAR schedule of the row's source (a later month) has posted. Verify posts `DEPOSIT_CREDITED` (metadata `reclassificationId`, `sourceLoanId`; never `loanId`, which marks the engine's own overpayment allocations) and recomputes the loan (trigger `RECLASS:<id>`).
- `loanPaymentRows` (repayments.ts) is the one place loan payments are read: each row's `net` = amount less verified reclassifications. The engine, the loan pages, the payoff quote and the statement all go through it. A correction can't reverse a row that has a reclassification.
- `creditMovements` gives a member's credit history with running balance (member credit page and the loan statement PDF).

## Bank, Track B (PRD F10)

- `src/modules/credit/banking/statements.ts`: go-live opening balances (Admin uploads with the statement as evidence; the Finance Manager commits, a different user; posts `OPENING_BALANCE`, source `LEGACY_IMPORT`, uniqueness `CREDIT:OPENING_BALANCE:<account>`; must be the `go_live_date` when that setting is set); statement import through the standard template or a column mapping saved per account (`StatementMapping`: header per field + date format ISO/DMY/MDY; the header row is found below any title lines).
- Statement rules: the lines must add up from the opening to the closing balance; the opening balance plus any lines already imported (an overlap) must equal the previous statement's closing balance, or the committed go-live balance for the first. Lines are keyed `account|date|direction|kobo|REFERENCE|running balance` (`#n` for repeats in one file); lines already imported are skipped, never duplicated.
- `matching.ts`: the system proposes (same account, same amount, ±3 days), a person decides. Finance Manager: `verifyLodgement` (credit ↔ declared lodgement → BANK_VERIFIED, `LODGEMENT_BANK_VERIFIED` status event), `tagDirectPayment` (credit → member, reference `DP-…` for the DIRECT row), `matchVoucher` (debit ↔ VERIFIED disbursement/refund voucher, permission `bankDebit.match`), `verifyBankLineEntry`/`returnBankLineEntry`. Cashier: `recordLodgement` (only BANK_VERIFIED with a statement line and a schedule; posts `CASH_IN` source `BANK_STATEMENT` + `LODGEMENT_APPLIED`; anything else is a `ForbiddenError` and the attempt is audited `lodgement.record.blocked`, AT-f), `recordBankLineEntry` (BANK_CHARGE debit, BANK_INTEREST credit, INTERNAL_TRANSFER either; verified entries post `CASH_OUT`/`CASH_IN`, source `BANK_STATEMENT`, `metadata.category`, never revenue).
- `ageingReport`: Unapplied Bank Credits (credit lines with no lodgement, no tag, no verified entry) and Unverified Lodgements, bucketed 0–30 / 31–60 / 61–90 / 90+ days (AT-g).
- Pages: `/staff/bank` (accounts, opening balances, mapping, statement import), `/staff/bank/matching` (Finance Manager), `/staff/bank/cashier`, `/staff/bank/ageing`. Template `/api/v1/templates/bank-statement.xlsx`.
- There is no endpoint for a Cashier to create a lodgement or a receipt from nothing.

## Statements, receipts and reports (PRD F13)

- PDFs: `src/lib/pdf.ts` (`PdfWriter`, A4 portrait or landscape) embeds Noto Sans from `assets/fonts/` (OFL, vendored) via `@pdf-lib/fontkit`, because the standard PDF fonts can't encode ₦. `next.config.ts` traces `assets/fonts/**` into the server bundle. Never switch back to `StandardFonts` for anything that prints money.
- The fonts are embedded whole (`subset: false`): pdf-lib's own subsetting silently dropped most glyphs (words printed blank, though the text could still be copied out). The files in `assets/fonts/` are therefore trimmed copies, made with fontTools `pyftsubset` from Noto Sans 2.x: Basic Latin, Latin-1 and Extended-A, combining accents (Yoruba, Igbo), general punctuation, arrows, ₦, ™, minus, ✓ ✗; layout feature `kern` only (ligatures printed `fi` with a gap). A character outside that set prints blank, so extend the set and regenerate if one is needed. Check a PDF visually after any font change.
- Guarantor form (`src/modules/credit/loans/guarantor-form.ts`, `/api/v1/guarantor-form[?loan=<id>]`, permission `guarantorForm.print`: Loan Officer): one A4 page for a non-member guarantor, blank or with the applicant filled in; downloads audited `guarantorForm.printed`.
- Member documents (`src/modules/credit/reports/member-documents.ts`): loan statement (`/api/v1/loans/<id>/statement`), payoff quote (`/api/v1/loans/<id>/payoff-quote`), receipt per remittance row (`/api/v1/receipts/<rowId>`). Served by `src/app/api/v1/documents.ts` to the member who owns the record or to staff with the right permission (and TOTP); every download is audited.
- Receipts: number `RC-<schedule reference>-<row>`; checksum = HMAC-SHA256 of the row id with `RECEIPT_SECRET` (falls back to `BETTER_AUTH_SECRET`), first 12 base64url chars. The QR code opens `/verify/<rowId>.<checksum>` (public, in the `(auth)` group): genuine or not, number, amount, date, masked name, reversed or not; 20 checks per minute per address (`src/lib/rate-limit.ts`, in memory, per instance). Changing the secret invalidates every printed receipt.
- Staff reports (`staff-reports.ts`, `REPORTS`): one definition renders on screen (`/staff/reports/<key>?from=&to=`), as Excel and as PDF (`/api/v1/reports/<key>?format=xlsx|pdf`, exports audited `report.exported`). Money stays kobo until display; Excel gets naira numbers with a ₦ format. Built: active loans register, expected vs actual collections, interest income, arrears, legacy loans and opening balances, joint reconciliation and exceptions, prior-period adjustments, Track A, Unapplied Bank Credits, Unverified Lodgements, Overpayment Credits, invitations and conversion, ledger export (`ledger.export`, Auditor). The audit extract is the existing `/staff/audit`.
- `tests/integration/reports.test.ts` ties report totals to ledger sums; keep it passing when a report changes.

## Rows shared across several loans (added 15 November 2026)

- A row naming no loan for a member with 2+ ACTIVE loans (a payroll voucher has no loan column) is split, not refused: `checkScheduleRows` orders the loans oldest first (d0, then created) and gives each up to its current instalment as at the row's payment date (`loanLiveState(...).next`, the same figure as the deduction schedule; rows of the same member in one file don't count an instalment twice). What is left over goes to Overpayment Credit (MOAUM's choice, 15 November 2026), under the row's usual `CREDIT:ROW:<id>:CREDIT` key. A row that names a loan still goes wholly to that loan.
- The schedule keeps one row per payroll line: the row has `loan_id` null and its parts are in `credit.remittance_row_split` (row, loan, position, amount). `loanPaymentRows` reads a loan's own rows plus its parts (same row id), so the engine, loan pages, statements and deduction schedule see them. `postRowExtras` writes parts and credit for schedules and correction replacements; reversing a row reverses its credit and recomputes every loan in its parts. Allocation keys now include the loan id. Split rows can't be reclassified.
- Dry run, schedule page, receipt ("Applied to") and the member's SMS list each loan's part and any credit.

## Reconciliation and month close (PRD F11)

- `src/modules/credit/reconciliation/reconciliation.ts`: `runReconciliation(month)` (Finance Manager, `reconciliation.run`), only after the month has ended, it isn't closed, and every active account with a committed opening balance has statements reaching month end + 3 days (`readiness`). Stores a `ReconciliationRun` (results JSON, kobo strings) and audits it.
- Equation (1), `accountPosition`: bank at month end = go-live opening + every imported line up to then; ledger cash = OPENING_BALANCE + CASH_IN − CASH_OUT for the account. Each cash event is tied to its statement line (Lodgement → its line, BankLineEntry → its line, CASH_OUT with `metadata.voucherId` → the voucher's matched line). Lines with no event, and events with no line by month end, are the reconciling items (unapplied credits, tagged not yet scheduled, verified not yet recorded, unrecorded debits, recorded debits/credits not yet on the statement). The remainder must be zero; otherwise a `LEDGER_BANK_DIFFERENCE` exception. Equation (2): recorded = verified + not yet paid − excess over all schedules to the month.
- Exceptions go in the portal-wide `shell.exception` register with stable dedupe keys: `SHORTFALL:<schedule>` / `EXCESS:<schedule>` (Track A), `IN_BANK_NOT_IN_SYSTEM:line:<id>`, `IN_SYSTEM_NOT_IN_BANK:lodgement|voucher:<id>`, `AMOUNT_MISMATCH:line:<id>`, `DUPLICATE:line:<id>`, `LEDGER_BANK_DIFFERENCE:<account>:<month>`. A rerun updates amounts; exceptions it no longer finds get `details.readyToClose` (still closed by the GMD). `verifyLodgement` refreshes the schedule's shortfall at once (`refreshScheduleException`). `ReconScope` exists only so tests can limit a run to their own account and source.
- Lifecycle (`src/shell/exceptions/exceptions.ts`): OPEN → UNDER_REVIEW (`reviewException`, Finance Manager, notes accumulate, optional SUPPORTING evidence) → CLOSED (`closeException`, GMD only, from UNDER_REVIEW, reason ≥ 10 chars and evidence required). Closing never touches the ledger. Page `/staff/exceptions`.
- Month close (`close.ts`, `month.close`, Finance Manager): in order (`nextMonthToClose`: the month after the last closed, or the first month with ledger activity), after it ended, with a run. Saves PDFs of the reconciliation and the month's reports as evidence (`SNAPSHOT_REPORTS`) and the month's ledger totals in `PeriodClose`. Never reopened. Events dated inside a closed month but posted after its close are prior-period adjustments (`adjustments.ts`, report "Prior-period adjustments"). Page `/staff/reconciliation`.

Shortfall/excess exceptions come from F11; the exception panel shows whatever is open in `shell.exception`.

## Evidence (PRD F3)

## Members (PRD F5)

- `src/modules/credit/members/`: `invitations.ts` (send, resend, revoke; 50 per sender per day, 3 per phone per week, counted from the audit trail), `registration.ts` (the `/join/<token>` flow), `review.ts` (Loan Officer activate/decline), `sources.ts` (remittance sources), `rules.ts` (form schemas, consent text and version).

- Members without an email get a `…@members.dommus.invalid` login email (the user table requires one).

- Member numbers: every member gets a system-issued `member_no` (`MCS-NNNNN`, Postgres sequence `credit.member_no_seq`, default on the column; existing members were numbered by creation date). - NDPA data copy: `/api/v1/me/data-copy?format=pdf|json` (`data-copy.ts`), any member-record owner, every download audited. The PDF uses standard fonts, which drop accents; the JSON keeps exact text.

The Admin member import (`member-import.ts`) is all or nothing: it re-validates on commit, and any error rejects the whole batch.
